01 / PURPOSE

자동 검사의 역할을 분명히 정합니다

Agent에게 “기존 구조를 유지하라”는 설명을 주고, 실행 도구로 그 설명의 주요 조건을 검사합니다. 작업 지침은 driver_lint/CLAUDE.md와 AGENTS.md, 구조·스타일 규칙은 config/rules.json, 공통 엔진은 src/driverlint/입니다. pablo_is/와 gdc/는 각각 policy·HW profile·reference·report·개발 지침을 가지며, 각 policy의 profile이 해당 담당자의 기본 과제를 선택합니다. 수정 내용은 diagnostic의 path:line · rule ID · severity · message · fix 형태로 표시됩니다.

37개 규칙Architecture, Style, Safety, Build, Interface, Review
변경 전후 비교기존 위반을 구분하고 새 위반·삭제·누락을 확인
담당자별 독립 검사Pablo IS와 GDC의 policy·scope·HW 선택·gate 분리

기본 gate는 error에서 실패합니다. IRQ context, DMA mapping, PM balance처럼 소스 패턴만으로 확정하기 어려운 사항은 warning으로 reviewer에게 전달합니다. --fail-on warning으로 경고까지 gate에 포함할 수 있습니다. checkpatch의 CHECK는 info입니다.

기존 소스를 모두 다시 포맷할 필요는 없습니다.

전체 audit는 기존 코드의 현황을 보여 줍니다. 평소의 scan은 Git 또는 release snapshot을 기준으로 새 진단을 보고합니다. 구조 검사는 파일 전체를 전후 비교하므로 config 삭제나 SPDX 제거처럼 새 줄만 보는 검사로 놓치기 쉬운 회귀도 확인합니다.

이 린터는 파일 경로와 lexical C 분석을 사용합니다. C compiler AST, 전처리기의 최종 분기, interprocedural call graph, DMA lifetime 또는 HW 동작을 증명하지 않습니다. 빌드·KUnit·실기 결과를 리뷰 자료에 함께 연결해야 합니다.

02 / QUICK START

소스 릴리스 폴더에서 실행하기

모든 검사 예제는 driver_lint/를 배치한 소스 릴리스 루트를 기준으로 합니다. 이 도구 저장소에는 원본 드라이버/커널 소스와 생성 보고서가 없으며, 해당 파일 항목은 텍스트로 표시합니다. pip 패키지는 필요하지 않습니다. Python 3.10 이상과 Perl을 사용하며, checkpatch는 적용 릴리스의 kernel-6.12/scripts/checkpatch.pl을 실행합니다.

python3 driver_lint/gdc/lint.py doctor

# 두 드라이버에 걸친 변경: 독립 결과를 함께 확인

# 담당자별 HTML 결과 (Pablo IS도 같은 방식)

# 새 release 원본: 반드시 수정 전에 담당 reference 준비

공유 파일: Kconfig, BUILD.bazel, post/Makefile, board fragment 두 개는 양쪽의 metadata 경로입니다. 각 profile에 등록한 해당 드라이버의 조건만 검증합니다. 공유 파일의 문법/스타일 오류는 양쪽 담당에 영향을 줄 수 있습니다. 공통 helper/API를 변경하면 해당하는 양쪽 검사와 review를 연결합니다.

현재 원본 1,813개 파일은 Pablo IS 1,756개 / GDC 62개로 나뉘며 공유 metadata 5개가 겹칩니다. 담당 production/KUnit source는 겹치지 않습니다. 원본 reference는 변경하지 않고 승인된 original object에서 범위별 manifest를 파생했습니다. driver_lint/lint.py는 이제 두 독립 검사를 조정하며, 기존 combined policy는 명시적 --policy 호환과 reference migration용으로 남겼습니다.

기본 --checkpatch auto는 변경 검사에서 bundled checkpatch를 실행합니다. --all/--files의 전체 파일 검사는 기본적으로 외부 checkpatch를 생략하며, 필요하면 --checkpatch on을 명시합니다. 모든 보고서는 실제 실행 engine과 생략 이유를 표시합니다.

04 / LAYER RESPONSIBILITY

기존 호출 방향을 reviewer와 agent가 공유합니다

버튼을 누르면 각 계층의 역할과 허용되는 의존을 볼 수 있습니다. 그림은 주된 제어 흐름입니다. 현재 코드의 모든 include 관계가 엄격한 단방향 DAG라는 뜻은 아닙니다.

→→→
Core / V4L2

사용자 요청, queue/buffer 상태, stream lifecycle, runtime PM과 scheduling 정책을 담당합니다. GDC는 공통 camerapp_hw_* API를 호출하며 직접 register offset이나 PMIO_SET_F를 추가하지 않습니다.

Camera Pablo

camera/is-*.c, interface/, include/
  → ischain/<project-selected-family>/
  → hardware/is-hw-*.c, pablo-hw-*.c
  → hardware/api/*
  → hardware/sfr/*

sensor/, vendor/, lib/, icpu/
  기존 공통 helper/type/adapter 경로 유지

GDC

pablo-gdc-core.c / pablo-gdc.h
  V4L2 M2M · vb2 · jobs · PM · IRQ dispatch
  → pablo-hw-api-gdc.h
  → pablo-hw-api-gdc-v<selected-IP-version>.c
  → pablo-hw-reg-gdc-v<compatible-register-version>.h
  → PMIO / HW

VOTF MFC adapter / HDR10+ helper
  해당 과제의 config·adapter와 HW 구현 선택

layer_patterns는 위에서부터 첫 match로 분류합니다. testing와 register 경로를 먼저 분류하고, GDC version API와 HDR10+ 구현을 gdc-api로 지정한 뒤 나머지 GDC 공통 경로를 gdc-core로 분류합니다. 잘못된 경로 분류는 rule의 오탐 원인이므로 새 IP를 추가할 때 먼저 확인해야 합니다.

checkpatch와 formatter의 차이

checkpatch는 새 patch의 brace, spacing, 선언, kernel API 사용 등 기존 Linux 규칙을 검사합니다. 환경별 ~/.checkpatch.conf가 결과를 바꾸지 않도록 임시 작업 폴더에 빈 설정을 둡니다. 프로젝트 규칙은 계층·과제별 HW 선택·빌드 연결·리뷰 신호를 추가합니다.

--clang-format은 kernel-6.12/.clang-format의 설정을 명시해서 replacement XML만 비교합니다. camera 폴더가 kernel 트리 바깥에 있기 때문에 단순한 --style=file의 상위 폴더 검색에 의존하지 않습니다. C/H를 직접 수정하거나 전체 파일을 자동 재포맷하지 않습니다. formatter가 설치되지 않았는데 요청한 경우 exit 2입니다.

checkpatch의 patch 제출 메타데이터 일부는 이 gate에서 제외합니다. Signed-off-by와 Change-Id는 실제 patch 제출 단계에서 별도로 확인하세요. C/H SPDX는 STYLE006이 관리하므로, 현재 소스의 C++ 형식 SPDX 첫 줄에 대한 checkpatch의 별도 경고는 제외했습니다.

현재 S947B profile의 변경 예제

아래 v14/v1400 경로는 현재 예제의 선택값입니다. 다른 과제에서는 해당 profile이 선택한 family/IP 구현으로 바꾸세요.

GDC core에 레지스터 쓰기를 추가한 경우

ARCH002 / ARCH003 core에 들어간 변경

/* pablo-gdc-core.c */
#include "pablo-hw-reg-gdc-v1400.h"

/* job 처리 경로 안에 새로 추가 */
PMIO_SET_F(pmio, GDC_R_IP_PROCESSING,
           GDC_F_IP_PROCESSING, 1);

수정 방향 공통 API를 통한 호출

/* 기존 core의 job 경로 */
camerapp_hw_gdc_start(pmio, clb);

/* HW 변경은 기존 target API에 구현 */
/* pablo-hw-api-gdc-v1400.c의 관련 함수 */
GDC_SET_F(pmio, GDC_R_IP_PROCESSING,
          GDC_F_IP_PROCESSING, 1);

위 예제는 수정 위치를 설명하는 코드입니다. 실제 start/reset 순서와 field 값은 해당 함수, HW 문서와 KUnit을 확인해야 합니다. core/control/API에 비슷한 helper를 중복 생성하기 전에 기존 공통 함수를 찾아 재사용하세요.

Agent가 GDC 파일 버전을 혼동한 경우

# v1400 API에서 아래 header를 추가하면 ARCH006 error
#include "pablo-hw-reg-gdc-v1500.h"

# 올바른 target register layout
#include "pablo-hw-reg-gdc-v1400.h"

# 다른 SoC의 is-v15_0_0 파일을 수정하면 ARCH007 warning
# 현재 s947b profile의 선택: ischain/is-v14_0_0/
# 차기 과제는 해당 profile이 선택한 family 구현을 수정

spinlock 안에 sleep 동작을 추가한 경우

spin_lock_irqsave(&gdc->slock, flags);
msleep(20); /* SAFE003 warning */
spin_unlock_irqrestore(&gdc->slock, flags);

필요한 상태를 lock 안에서 복사한 뒤, atomic context 밖의 기존 work/thread 경로에서 기다리는 방향을 검토합니다. lock을 단순히 이동하면 race가 생길 수 있으므로 state ownership과 IRQ 호출 문맥을 함께 설명해야 합니다.

기존 위반과 새 위반의 비교 방식

프로젝트 규칙은 같은 파일의 before/after를 검사하고 path + rule + message + evidence의 발생 횟수를 비교합니다. 줄 번호가 이동해도 같은 위반을 새로 발행하지 않습니다. 같은 잘못된 statement를 추가 복제한 경우는 발생 횟수가 늘어나므로 새 진단을 발행합니다. 기본 공백/줄 길이 검사는 변경된 줄에 집중하고, build mapping·SPDX·파일 끝 LF처럼 파일 전체의 조건은 전후 비교합니다.

public header, export, register/tuning table, target 외 version, 신규 C source 및 큰 diff에는 변경 자체에 대한 review warning을 추가합니다. 따라서 기존 위반이 그대로여도 인터페이스/데이터/선택 경로의 변경은 reviewer에게 보입니다.

Git의 rename은 삭제+추가로 다루며 source 누락을 숨기지 않습니다. scope 안의 ignored source additions도 포함합니다. 현재 root가 어떤 상위 Git 저장소의 부분 폴더일 뿐이면 release snapshot 모드를 사용합니다. 검사 대상 source symlink와 workspace 밖 경로는 명시적 실패입니다.

id / device / soc / evidence과제 식별과 선택 근거. 마케팅 SoC 이름에서 버전을 추정하지 않고 HW 문서와 source/build 선택을 확인
camera_root / scope / scope_include / scope_excludeworkspace 기준 source root와 검사할 module/fragment 경로. positive include / negative exclude로 담당 경로를 나누고, 파일명·확장자·exclude는 담당 policy와 함께 적용
version_domainsPablo IS는 family domain 1개와 필요한 IS IP domain들, GDC는 family 없이 GDC IP domain만 사용합니다. 각 domain의 selected_versions는 독립된 목록이며 검증된 복수 선택도 가능. 선택 버전은 source/build mapping에 나타나야 하며 label과 기대 source가 충돌하면 설정 오류. 목록에 없는 구현 수정은 ARCH007 review warning; 문서화된 compatible register는 선택에 포함
path_patterncamera_root 기준 상대 source 경로에서 버전을 추출하는 정규식. 정확히 한 개의 capturing group을 사용. 차기 HW의 명명 방식이 달라지면 profile의 pattern도 갱신
include_patternfamily domain의 header include 경로에서 family를 추출. 해당 family 구현은 자기 family 또는 문서화된 include_compatibility를 사용
implementation_pattern / register_pattern각 IP의 API source와 register include 버전을 각각 추출. 기본은 같은 버전이며 ARCH006으로 pairing 검사. profile에 등록한 IP에만 적용
camera_familiesPablo IS의 IP 구현이 사용할 수 있는 camera family 목록. IP 버전과 family 숫자가 같을 필요는 없음. IS에서 생략 시 선택한 family 목록 사용. GDC profile에는 등록하지 않음
register_compatibility / include_compatibility구현 version → versions + reason + evidence를 매핑. HW 재사용·조건부 layout 선택의 실제 근거 필요. 린터는 HW 호환성 자체를 증명하지 않음
common_family_selectors공통 compile-time family dispatch가 필요한 특정 경로의 path + reason + evidence. path는 camera_root 기준이며 fnmatch 사용. 전처리기 조건은 별도 검토
fragments파일마다 path + requirements + exclusive_groups. requirements는 CONFIG_*의 y/m/n, exclusive_groups는 config pattern과 허용 selected 목록. 값 누락/변경/중복 및 선택 밖 enable 검사
build_contracts.kconfigpath/symbol과 선택적 depends_on 조건. 특정 SoC 의존과 필요한 config 선언을 검사
build_contracts.kbuildpath/target/config/sources/exact와 선택적 versioned_source_pattern. 줄 연결 후 literal object 선택을 검사. exact=false이면 공통 object와 다른 IP의 object를 함께 둘 수 있음
build_contracts.ddk / selectorsDDK의 module/config True branch와 기대 source 목록, board group의 name/boards 및 keyword(기본 match_any). profile이 선택한 source 밖의 versioned_source_pattern match를 검출
build_contracts.literals선택적 name/keyword/values mapping. selector가 있으면 select의 해당 branch, 없으면 literal list 또는 glob의 입력 목록을 검사. ischain include 경로, family filegroup, 재사용 IP source 연결 확인
protected_sources / review_variants해당 담당이 선택한 HW 구현·register의 필수 경로와 빌드 variant. 보호 source 또는 등록된 build/fragment 삭제는 BUILD005. profile-only에서 필수 파일 누락은 exit 2

차기 SoC 또는 HW version으로 전환하는 절차

  1. 변경 HW의 specification, family parameter layout, 공통 API 계약, Kconfig, Makefile, Bazel selector와 최종 .config를 확인합니다. family/API/control/register의 version을 IP별로 확인합니다.
  2. 과제별 profile을 만들고 scope, version_domains, register/include compatibility, fragment, source/object/filegroup/include 선택, 보호 경로와 빌드 variant를 갱신합니다. 새 version 자체를 error로 막는 규칙은 추가하지 않습니다.
  3. HW별 차이는 해당 family/IP 구현에 반영합니다. 공통 buffer/PM/lifecycle 코드는 공통 계약으로 호출하며 explicit version header나 register offset을 새로 결합하지 않습니다. 공통 API 변경이 필요한 경우 호출자/ABI 영향과 전환 방식을 함께 검토합니다.
  4. --profile-only로 등록된 현재 build/HW 연결을 전부 검사하고 정상 source gate를 실행합니다. --all은 기존 source에 대한 규칙 영향 조사입니다. build/KUnit/실기 검증을 과제별로 수행합니다.
  5. policy.profile을 새 profile 경로로 변경해 hooks와 기본 CLI가 같은 과제를 사용하게 합니다. source/HW 변경과 profile 변경을 같은 리뷰에서 근거와 함께 확인합니다.

--profile NAME은 policy 폴더의 profiles/NAME.json을 읽습니다. JSON 경로를 지정하면 --root 기준으로 해석하며, 지정하지 않으면 policy.profile을 사용합니다. CLI의 일회성 --profile 지정은 hook의 기본 과제를 바꾸지 않습니다. 잘못된 schema/pattern, 근거 없는 compatibility, scope 밖의 계약 경로는 설정 오류(exit 2)입니다.

--profile-only는 변경 유무와 관계없이 등록된 파일의 ARCH006/008, BUILD003/004/005를 확인합니다. 기본 외부 엔진은 실행하지 않으며, normal scan의 새 코드 구조·스타일 검사나 실제 select/glob evaluation을 대체하지 않습니다. Pablo IS profile은 Pablo family/YUVP, GDC profile은 GDC IP/register 재사용을 별도로 모델링하며 모든 IP를 자동 추론하지 않습니다.

같은 scope에서 profile만 바꾸면 원본 source bytes와 reference manifest는 유지됩니다. snapshot 생성 시의 policy hash와 달라지면 scan이 이를 note로 표시합니다. 선택 연결은 --profile-only, 새 규칙 영향은 --all로 확인하면 되며 profile 변경 때문에 기준선을 덮어쓸 필요는 없습니다. scope가 달라지면 reference가 호환되지 않으므로 새 과제 원본의 범위를 확인하고 수정 전에 해당 원본 reference를 준비합니다.

위 값은 현재 예제 경로의 설명용 설정입니다. 실제 source와 register contract를 확인한 뒤 적용합니다. 적용한 예외는 JSON의 suppressed에 원래 진단·reason·owner를 함께 남기고 text/HTML에도 표시합니다. owner/reason 없는 예외와 알 수 없는 rule ID는 설정 오류입니다. source의 nolint 주석은 해석하지 않습니다.

  1. 오탐 또는 필요한 구조 변화의 source 근거를 확보합니다.
  2. 계층/threshold/exception 중 필요한 작은 설정을 바꾸고 catalog의 탐지 설명과 제한을 갱신합니다.
  3. 회귀 테스트와 scan --all --checkpatch off로 기존 source 영향을 확인합니다.
  4. 공통 규칙 변경과 과제 HW 선택 변경의 목적을 리뷰에 설명합니다. 위반을 숨기기 위해 규칙이나 reference를 바꾸지 않습니다.

Android repo처럼 Git 저장소가 여러 개인 경우

제공한 commit gate는 하나의 실제 Git root에 scope source, policy/profile, 등록 build contract가 추적되는 모델입니다. 현재 release의 상대 경로를 그대로 camera 하위 Git root에 적용할 수는 없습니다. 실제 저장소 경로에 맞춘 per-repository profile을 준비하고, 다른 Git root의 device fragment 등 교차 계약은 승인된 manifest/revision을 사용하는 통합 CI checkout에서 검사해야 합니다. 이 installer는 여러 독립 index를 자동으로 합치지 않습니다. CI runner에는 승인된 checkpatch와 dictionary도 포함해야 합니다.

로컬 pre-commit은 git commit --no-verify로 우회할 수 있습니다. 팀 작업 지침은 우회를 금지하고, 서버에서는 아래 필수 CI를 merge 조건으로 적용합니다. Git의 hook 실행 시점, nonzero 종료의 commit 중단과 bypass 옵션은 Git 공식 문서에 정의되어 있습니다.

서버 CI: 승인된 linter로 committed 변경 검사

integration/ci-gate.sh와 scripts/run_ci.py를 제공합니다. 리뷰 시스템에 driver-lint-pablo-is, driver-lint-gdc 두 job을 등록하고 각 job의 component를 서버에서 고정합니다. shell step을 사용할 때는 보호된 job 설정의 DRIVER_LINT_COMPONENT=pablo-is 또는 gdc로 선택합니다. job definition과 bootstrap, 리뷰 기준 ref, Python/Perl/PATH는 서버의 보호된 설정에서 지정합니다. 아래 step도 보호된 기준 브랜치 또는 서버 설정에서 읽습니다.

# CI가 지정한 destination branch를 충분한 history와 함께 fetch한 상태
# 보호된 서버 job에 아래 step을 저장하는 예
set -eu
DRIVER_LINT_REVIEW_BASE=origin/main
review_base="$(git rev-parse --verify --end-of-options \
  "${DRIVER_LINT_REVIEW_BASE}^{commit}")"
base="$(git merge-base "$review_base" HEAD)"
temporary="$(mktemp -d)"
trap 'rm -rf "$temporary"' EXIT HUP INT TERM
git show "$base:driver_lint/scripts/run_ci.py" > "$temporary/run_ci.py"
# Pablo IS job
python3 -I "$temporary/run_ci.py" --root "$PWD" --base "$base" \
  --component pablo-is --format json \
  --output driver_lint/pablo_is/reports/ci-gate.json

# GDC job에서는 위 준비 단계 후 이 담당 명령을 실행
python3 -I "$temporary/run_ci.py" --root "$PWD" --base "$base" \
  --component gdc --format json \
  --output driver_lint/gdc/reports/ci-gate.json

bootstrap은 base의 src/, rule catalog, commit gate, bundled checkpatch를 별도 임시 폴더에 추출합니다. Python isolated mode로 이 엔진을 실행하고 제출된 HEAD의 source/config/profile은 Git blob 데이터로 검사합니다. 제출된 Python·Perl·build 코드를 실행하지 않습니다. BASE..HEAD를 읽으므로 이미 commit된 변경도 포함하며, CI worktree의 추가 편집으로 결과를 가리지 못합니다. job은 exit 1과 2를 실패로 처리하고 담당의 reports/ci-gate.json을 보관합니다. selector 생략 또는 --component all은 두 독립 결과를 모으는 coordinator이며, 서버에서는 위와 같이 별도 필수 status로 연결합니다.

기본 CI는 각 담당 common policy를 base와 비교해 profile 경로 선택만 변경할 수 있게 합니다. 차기 SoC에서는 HW profile과 해당 구현/build를 정상적으로 변경할 수 있으며, Exynos2600·PABLO_V14_0_0에 고정하지 않습니다. profile 내용의 정확성, scope 축소, 호환 근거의 타당성은 HW 담당자의 필수 review로 확인합니다. data profile을 검증한다고 HW specification의 진위를 자동으로 증명하는 것은 아닙니다.

공통 규칙 자체를 발전시키는 maintenance 경로

common policy/engine을 변경하는 PR은 기본 gate의 common lock으로 실패합니다. 도구 담당자가 규칙 영향, 회귀 테스트, 오탐과 전체 audit를 검토한 뒤 별도 보호된 maintenance job에서 승인된 tool SHA를 지정합니다. source diff의 base와 trusted runner revision을 독립적으로 지정할 수 있습니다.

# APPROVED_TOOL_SHA는 review 후 서버 관리자가 지정한 tool revision
# 이 bootstrap 자체도 보호된 기준/승인된 패키지에서 준비
python3 -I "$temporary/run_ci.py" --root "$PWD" --base "$base" \
  --runner-ref "$APPROVED_TOOL_SHA" --format json \
  --output driver_lint/reports/ci-gate.json

승인 revision의 common policy와 엔진을 사용하고 제출 source는 계속 BASE..HEAD로 검사합니다. PR label, branch 환경변수, agent 옵션으로 임의 SHA나 pass override를 선택하게 하면 안 됩니다. 일반 driver 변경과 새 과제 profile 선택은 이 maintenance 경로를 요구하지 않습니다.

필수 status와 소유자 review를 함께 설정합니다

  1. 승인된 원본 driver + linter/config/profile baseline을 대상 branch에 먼저 도입합니다. bootstrap이 없는 과거 base에서는 CI를 실행할 수 없으므로 초기 인프라 도입은 human review로 완료한 뒤 필수 job을 켭니다.
  2. 리뷰 시스템에서 driver-lint-pablo-is와 driver-lint-gdc를 merge의 필수 status로 등록하고, 정상 commit에서 성공·위반 commit에서 실패하는지 확인합니다. skip/실행 누락이 merge 성공으로 인정되지 않게 설정합니다.
  3. 공유 검사 엔진은 도구 담당, 각 policy/예외/profile은 해당 driver 담당에게 review를 배정합니다. hook/plugin/AGENTS/CLAUDE 지침과 CI 설정 변경도 담당자에게 배정합니다. 공유 metadata/API 변경에 필요한 양쪽 승인은 리뷰 서버의 절차로 요구합니다.
  4. 일반 push, force push, admin bypass 등 대상 branch의 변경 경로에도 팀의 같은 검사·승인 조건을 적용합니다.

GitHub 예제는 CODEOWNERS.example입니다. 실제 팀 이름으로 바꾸고 .github/CODEOWNERS 등에 배치한 뒤 required code-owner review를 켭니다. CODEOWNERS 파일 자체도 보호 대상에 포함합니다. GitHub의 설정 조건은 protected branch 공식 문서와 CODEOWNERS 공식 문서를 따릅니다. 다른 리뷰 서버는 동일한 필수 job/submit 조건으로 매핑합니다. 이번 작업에서 외부 서버 설정을 변경하지는 않았습니다.

GitHub CODEOWNERS에서 한 파일에 두 팀을 나열해도 어느 한 owner의 승인으로 조건이 충족됩니다. 공유 파일에 두 팀의 승인이 모두 필요하면 추가 리뷰 규칙이나 승인 절차를 구성해야 합니다. 공식 code-owner 승인 조건
