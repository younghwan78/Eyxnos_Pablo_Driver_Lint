Claude/Codex는 --component pablo-is handler를 설치하며 OpenCode는 driver-lint-pablo-is.js로 구분합니다. 다른 담당 adapter는 유지하며 같은 selector의 --remove로 제거합니다. Codex는 바뀐 정의를 새 세션 /hooks에서 검토·신뢰해야 합니다. 공식 hook 정책 · Claude 공식 hooks · OpenCode plugins

OpenCode V2 runtime에서는 v1 대신 v2 adapter를 선택합니다. API 전환은 이전 API/동일 component로 --remove 후 설치합니다. 실제 OpenCode 실행 파일은 이 환경에 없습니다.

Git은 pre-commit 하나를 사용하므로 선택한 담당 gate 또는 all을 연결합니다. 이전 owned driver gate로 교체할 때 중복 실행하지 않으며 기존 team hook은 먼저 실행하고 제거 시 복원합니다. commit gate는 Git index의 실제 source/settings와 등록된 build contract를 검사합니다. unstaged 수정으로 stage 오류를 숨길 수 없고 commit --only의 임시 index도 읽습니다. Hook은 --no-verify로 우회할 수 있으므로 서버 CI가 필수입니다. Git 공식 hooks

현재 release root는 Git 저장소가 없어 실제 Git hook은 미설치입니다. 임시 실제 Git 저장소에서 담당별 commit 차단을 검증했습니다.

서버가 준비한 protected/base bootstrap을 실행하고 충분히 fetch한 review base를 지정합니다. 제출 branch의 엔진을 실행하지 않고 승인된 엔진/catalog/checkpatch로 committed BASE..HEAD와 이 담당의 제출된 policy/profile/build 계약을 검사합니다. CI의 설정은 committed HEAD에서 읽습니다. 이 담당 common policy를 approved revision에 고정하며 HW profile 선택은 근거와 review로 변경할 수 있습니다.

cross-driver branch는 각 담당의 required job으로 모든 변경을 검증합니다. common engine/catalog는 도구 담당, pablo_is/config와 HW profile은 해당 driver 담당이 리뷰합니다. Shared metadata는 양쪽 담당을 배정하고 필요한 양쪽 승인은 리뷰 서버의 절차로 요구합니다. GitHub CODEOWNERS 여러 명만으로 두 팀 모두의 승인이 강제되지는 않습니다. 공식 CODEOWNERS 설명

도구 변경은 별도 reviewed maintenance job의 server-approved runner-ref를 사용합니다. PR 입력으로 runner SHA/skip/pass override를 선택하지 않습니다. multi-repository Android repo는 repository별 scope와 승인된 manifest 기반 통합 CI를 준비해야 하며, 이 gate는 독립 Git index들을 자동 합치지 않습니다.

이 패키지의 layer/scope와 HW domain에 적용되는 규칙만 실행됩니다. 아래 severity는 현재 담당 policy 기준입니다. GDC 전용 core register/4K rule은 Pablo IS 문서에서 제외합니다. compiler AST/effective preprocessor나 HW specification 의미를 검증하지 않습니다.

ARCH001 · production에서 .c include 금지 error

목적
구현 파일을 포함하면 모듈 경계와 translation unit이 합쳐집니다.
탐지
testing 이외 C/H의 literal #include 경로가 .c로 끝남
수정
공개 header에 선언하고 Makefile/DDK source에 구현을 연결하세요.
한계
KUnit의 기존 .c include는 허용하며 macro include는 해석하지 않습니다.

ARCH002 · 상위 계층의 SFR 직접 의존 금지 error

목적
core/ischain/interface가 register layout에 결합되면 HW API 교체가 어려워집니다.
탐지
core, ischain, gdc-core, interface에서 is-sfr/pablo-sfr/pablo-hw-reg header include
수정
해당 IP의 공통 HW API header를 사용하고 register 접근은 하위 구현으로 옮기세요.
한계
파일명과 경로 기반 규칙이며 hw-control의 기존 SFR 의존은 별도로 금지하지 않습니다.

ARCH004 · HW API에서 상위 manager 의존 금지 error

목적
HW API가 device/group/video manager를 알면 제어 흐름이 역전됩니다.
탐지
hw-api/gdc-api가 policy.upper_layer_headers의 header를 포함
수정
필요한 작은 parameter/type을 API 인자로 전달하세요. 기존 pablo-gdc.h와 is-hw.h는 허용합니다.
한계
기존 HW API가 공유하는 상위처럼 보이는 모든 type을 일괄 금지하지 않습니다.

ARCH005 · production에서 test 전용 의존 금지 error

목적
테스트의 fixture/mock이 실 드라이버에 들어가는 것을 막습니다.
탐지
testing 외부에서 단순한 positive KUnit guard 없이 testing/, kunit/test.h, kunit/mock.h, *-kunit-test.* include
수정
test helper는 testing 아래에 두고 production 지원 코드는 명확한 KUnit config guard로 제한하세요.
한계
KUNIT_EXPORT_SYMBOL과 기존 #if IS_ENABLED(CONFIG_PABLO_KUNIT_TEST)는 허용합니다. 복잡한 전처리 식은 평가하지 않습니다.

ARCH006 · IP API와 register layout의 호환성 검사 error

목적
각 IP의 구현과 register layout을 그 HW에 맞게 연결합니다. Pablo family와 IP 버전은 독립입니다.
탐지
profile.version_domains의 implementation_pattern/register_pattern으로 추출한 버전의 불일치
수정
해당 IP의 HW spec/build 근거로 register header를 선택하세요. 재사용이 필요한 경우 profile의 register_compatibility에 versions/reason/evidence를 기록하세요.
한계
등록된 IP의 explicit include만 검사합니다. 조건부 분기 및 HW spec의 실제 호환성은 평가하지 않습니다.

ARCH007 · 과제 선택 외 family/IP 구현 변경 검토 warning

목적
여러 HW 버전이 함께 있어 다른 과제의 구현을 수정할 수 있습니다.
탐지
수정 경로의 version_domains.path_pattern 버전이 selected_versions 또는 선택 IP의 문서화된 compatible register 밖인 경우
수정
활성 profile과 실제 선택 경로를 확인하세요. 차기 HW 과제이면 profile을 갱신하고, 여러 과제에 대한 의도적인 수정이면 영향 범위를 설명하세요.
한계
warning이며 새 버전 자체를 금지하지 않습니다. audit에서는 발행하지 않으며 profile에 등록한 version domain만 검사합니다.

ARCH008 · 공통 코드의 HW family 결합 및 비호환 include 검사 error

목적
공통 API/정책과 HW별 parameter/config layout을 분리하고 버전 간 계약 혼합을 확인합니다.
탐지
공통 계층의 explicit family include, family 구현의 다른 family include, 선택된 IP 구현의 profile.camera_families 밖 include
수정
공통 코드는 공통 header/API를 사용하고 HW별 구현은 해당 profile의 family를 사용하세요. 의도적인 family dispatch/reuse는 common_family_selectors 또는 include_compatibility에 근거를 기록하세요.
한계
explicit 경로만 검사합니다. 컴파일러 include search path와 조건부 분기는 평가하지 않습니다. 공통/API 계약의 정당한 변경은 별도 리뷰 대상입니다.

STYLE001 · 줄 끝 공백 warning

목적
불필요한 diff를 줄입니다.
탐지
변경/추가된 줄의 trailing space/tab
수정
해당 줄 끝의 공백만 제거하세요.
한계
원본 전체의 공백을 자동 정리하지 않습니다.

STYLE002 · space만 사용한 기본 들여쓰기 warning

목적
Linux driver는 기본 들여쓰기에서 tab 8칸을 사용합니다.
탐지
변경된 C/H 줄이 8칸 이상의 space로 시작하고 continuation/comment로 보이지 않음
수정
주변 코드와 맞춰 기본 indent를 tab으로 바꾸고 continuation 정렬은 유지하세요.
한계
continuation은 lexical 추정입니다. checkpatch와 reviewer 판단을 함께 사용하세요.

STYLE003 · 지나치게 긴 줄 warning

목적
리뷰 화면에서 제어 흐름을 쉽게 읽도록 합니다.
탐지
tab 8칸 확장 후 policy.max_line_length(100) 초과하는 변경 줄. 명시된 SFR/setfile/network table 경로는 제외
수정
자연스러운 인자/조건 경계에서 줄을 나누세요. kernel .clang-format은 ColumnLimit 80입니다.
한계
100은 review 경고 기준입니다. 표 경로는 줄 길이만 제외하며 변경 자체는 REVIEW001로 검토합니다. checkpatch는 자체 기준을 그대로 적용합니다.
